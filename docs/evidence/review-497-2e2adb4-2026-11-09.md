## Confirmed
1. **ensureLinks makes no row writes.** It does only three things, and never runs VALIDATE:
   - `create index if not exists`;
   - `add constraint ... not valid`;
   - it catches 42710 on a race.
2. **repairAndValidateLinks keeps each link separate.** Each link runs cleanup and then validate inside one transaction, so a failed validate rolls back that link's repair. It is reachable only from scripts/db-link-repair.ts.
3. **The cleanups match their delete rules.**
   - cascade means delete, set null means empty, and a missing parent is re-created;
   - none of them touches score columns or snapshots.
   - The only DELETE is on weekly_email_sends. Its `user_id` is NOT NULL in production and there are 0 null rows, so it cannot remove rows that have no user.
4. **The fingerprint covers every app table**, and it excludes only the four declared repair columns.
5. **The rehearsal on an isolated copy matches what the dossier expects:**
   - holdings and pe_runs change in the link column only;
   - visitors gain 32 rows;
   - all 45 FKs are validated afterwards.

## Notes (none blocking)

**N1, step 2 on live production.** The check that `--apply` is "unexpected-change free" assumes nobody else writes during the run. On live production, normal traffic would show up as UNEXPECTED and give exit 1 even when the repair was correct. Examples:
- new `events` and `visitors` rows from visits;
- a new bes or pe run adding holdings or pruning runs;
- weekly sends.

Also, exit 1 is reported only after each link's repair has already committed.

Recommendation: in the dossier, run step 2 in a quiet window with the bes, pe and weekly schedulers paused, and say that an UNEXPECTED row in a traffic table is triaged against the app's own writes, not rolled back by reflex.

**N2, index race at the first boot.** About 11 modules call ensureLinks on first use, and on several connections. Two parallel `create index if not exists` statements with the same name can fail with 23505 or 42P07. Only 42710 is caught, and only for the constraint.

The effect is transient: that module's `ready` resets and the next call succeeds. A one-line catch, like the constraint's, would remove it. Optional.

**N3, no lock_timeout on the boot ALTERs.** The NOT VALID FK takes SHARE ROW EXCLUSIVE on the parent too, for example `users`. A long transaction on the parent would leave the boot waiting, with the other queries queued behind it.

The tables are small and the risk is low. `set lock_timeout` around ensureLinks would bound it. Optional.
